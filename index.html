1. Visão Geral do Projeto

O problema

Clínicas multidisciplinares (psicologia, fonoaudiologia, terapia ocupacional, fisioterapia etc.) costumam controlar pacientes, agendas e repasses de profissionais com planilhas, agendas de papel e mensagens soltas. Isso gera choque de horários, dados sensíveis de saúde espalhados sem controle de acesso, retrabalho no faturamento de convênios e falta de indicadores para a gestão.

A solução proposta

O Vindix é uma aplicação web multiempresa (cada clínica tem seu próprio banco de dados) que centraliza:

Cadastros
Pacientes, profissionais e responsáveis, com validação rigorosa (CPF, telefone, e-mail, carteirinha).
Agenda
Agendamentos únicos e recorrentes com detecção de conflito e sincronização com o Google Agenda.
Consultas e evolução
Registro dos atendimentos realizados e histórico do paciente.
Convênios e financeiro
Guias, registro ANS, preços por especialidade e repasse dos profissionais.
Permissões granulares
Códigos de permissão por tabela e por ação, com histórico de alterações.
LGPD
Campos sensíveis criptografados, termos de aceite, exportação de dados do titular.

Arquitetura

As conexões com os bancos das clínicas ficam num cache LRUCache de pools (conexaoBD.js), para que o servidor atenda várias empresas sem abrir conexões ilimitadas.

Nível 3Validação Léxica com Expressões Regulares e AFD

Na hierarquia de Chomsky, as linguagens regulares (Tipo 3) são exatamente as reconhecidas por Autômatos Finitos Determinísticos, e toda expressão regular pode ser convertida num AFD. Um AFD usa memória constante (só o estado atual) e decide se aceita uma entrada de tamanho n em O(n), lendo cada caractere uma única vez. Por isso é o modelo ideal para a "porta de entrada" do sistema: todo dado vindo do formulário passa por um reconhecedor regular antes de chegar ao banco.

3.1 Onde isso está no Vindix

O arquivo FonteJS/source/regras.js define, para cada campo de cada tabela, um tipo, um tamanho máximo e uma expressão regular. A função normalizar() rejeita qualquer entrada fora da linguagem com { erro: 'formato inválido' }.

3.2 AFD do campo Data

A expressão ^\d{4}-\d{2}-\d{2}$ corresponde ao AFD abaixo (Σ = dígitos ∪ {"-"}; qualquer transição não desenhada vai para um estado de erro implícito):

d = qualquer dígito 0–9. Estado inicial q0, estado de aceitação q10. Memória: 11 estados, independentemente do tamanho da entrada.

3.3 O limite do modelo — e como o código respeita esse limite

Um AFD reconhece o formato AAAA-MM-DD, mas "30 de fevereiro" ou "mês 13" exigem regras semânticas. E o dígito verificador do CPF é uma soma ponderada módulo 11.

O grupo separou as duas responsabilidades: a regex faz a análise léxica e uma segunda etapa faz a verificação semântica. Na data, dataValida(a, m, d) monta um Date e confere se ele "volta" igual. No CPF:

export function cpfValido(cpf) {
    if (!/^\d{11}$/.test(cpf) || /^(\d)\1{10}$/.test(cpf)) return false;  // filtro léxico
    for (const t of [9, 10]) {                                           // dígitos verificadores
        let soma = 0;
        for (let i = 0; i < t; i++) soma += Number(cpf[i]) * (t + 1 - i);
        if ((soma * 10) % 11 % 10 !== Number(cpf[t])) return false;
    }
    return true;
}

Observação de teoria: /^(\d)\1{10}$/ usa uma retrorreferência (\1), recurso que vai além das linguagens regulares em geral. Aqui ela é inofensiva, porque o alfabeto é finito (10 dígitos): a linguagem "11 dígitos iguais" tem só 10 palavras, logo é finita e portanto regular, equivalente a 0{11}|1{11}|…|9{11}. Ou seja, continua cabendo num AFD.

Na prática, o dígito verificador do CPF também pode ser reconhecido por um AFD: como a soma é feita módulo 11, basta guardar (posição, soma mod 11), um número finito de estados. O grupo preferiu o laço por clareza; os dois têm custo O(n) e memória O(1).

3.4 Permissões como linguagem regular

Os códigos de permissão (Observacoes.txt) formam uma linguagem regular de dois símbolos: 1 | 2 | [1-6][0-5] | 50, em que o 1º dígito é a tabela (1 cadastros, 2 consultas, 3 especialidades, 4 agendamentos, 6 financeiro) e o 2º é a ação (0 geral, 1 acessar, 2 inserir, 3 alterar, 4 excluir, 5 histórico). O middleware exigirPermissao(1, 10, 12) em cada rota da API funciona como um reconhecedor: a requisição só é aceita se o usuário tiver algum dos códigos listados.

3.5 Por que isso importa (segurança e ReDoS)

  • Todas as regex são ancoradas (^…$), então o reconhecedor aceita a palavra inteira, nunca um pedaço dela. Isso impede injeção de conteúdo extra.
  • Os campos têm tamanho máximo (max) verificado antes da regex, e as buscas são truncadas em 100 caracteres (filtroBusca).
  • As expressões usadas não têm quantificadores aninhados ambíguos (como (a+)+), que fariam o motor de backtracking do JavaScript ter custo exponencial (ataque ReDoS). Elas se comportam como um AFD de custo linear.

Nível 2Análise Sintática e Autômatos de Pilha

Toda a comunicação entre o front-end e a API do Vindix é feita em JSON. O JSON é uma linguagem livre de contexto (Tipo 2): objetos e listas podem se aninhar em qualquer profundidade e cada {/[ precisa ser fechado na ordem certa. Pelo Lema do Bombeamento para linguagens regulares, a linguagem dos colchetes balanceados { [ⁿ ]ⁿ } não é regular: nenhum AFD, com memória finita, consegue "contar" n aberturas pendentes. Para isso é preciso uma pilha, ou seja, um Autômato de Pilha (AP).

4.1 Onde isso está no Vindix

// server.js
app.use(express.json({ limit: '100kb' }));
...
if (status === 413) return res.status(413).json({ erro: 'Conteúdo grande demais' });
if (status < 500)   return res.status(status).json({ erro: 'Requisição inválida' });

O express.json faz o JSON.parse do corpo de toda requisição. Esse parser é descendente recursivo, e a pilha de chamadas faz o papel da pilha do AP. Um payload mal formado (chave sem fechar, vírgula sobrando) é rejeitado antes de chegar a qualquer regra de negócio, com HTTP 400.

4.3 Exemplo didático: o reconhecedor de balanceamento

// Autômato de pilha simplificado: reconhece { } [ ] balanceados, ignorando strings
function balanceado(texto) {
  const pilha = [], par = { '}': '{', ']': '[' };
  let emString = false, escape = false;
  for (const c of texto) {                 // O(n): cada símbolo lido uma vez
    if (emString) { if (escape) escape = false; else if (c === '\\') escape = true; else if (c === '"') emString = false; continue; }
    if (c === '"') emString = true;
    else if (c === '{' || c === '[') pilha.push(c);
    else if (c === '}' || c === ']') { if (pilha.pop() !== par[c]) return false; }
  }
  return pilha.length === 0 && !emString;
}

Repare na composição dos níveis: o estado emString/escape é uma parte finita (um AFD embutido para reconhecer strings), e a pilha é a memória extra que só o Nível 2 oferece.

4.4 Limitando a memória do AP

Um AP teórico tem pilha infinita, mas um servidor real não tem. O limite de 100 kb no corpo da requisição limita o tamanho da entrada e, com isso, a profundidade máxima da pilha. Isso protege o servidor de payloads gigantes ou profundamente aninhados (negação de serviço). Somado a isso, toobusy-js e express-rate-limit cortam a carga quando o laço de eventos está saturado.

4.5 Depois da sintaxe vem a semântica

Um JSON sintaticamente válido ainda pode ser inválido para o negócio. Depois do AP vem a etapa léxica/semântica da seção 3: regras.js percorre cada campo esperado, rejeita tipos errados ('deve ser texto', 'deve ser um número inteiro') e aplica as regex. O pipeline completo é:

bytes → AP (JSON.parse) → AFDs por campo (regras.js) → regras de negócio (conflito, permissão) → banco

5.2 A verificação de conflito: um problema em P

Dois intervalos [i₁, f₁) e [i₂, f₂) se sobrepõem se, e somente se, i₁ < f₂ e f₁ > i₂. É exatamente essa condição que a consulta de conflitoAgendamento() usa:

SELECT FIRST 1 A.ID_TERAPEUTA FROM AGENDAMENTOS A
 WHERE A.STATUS = 'AGENDADO' AND A.ID <> ?
   AND (A.ID_TERAPEUTA = ? OR A.ID_PACIENTE = ?)
   AND A.DT_HR_AGENDADA < ?               -- início existente < fim novo
   AND DATEADD(... A.TEMPO_PREVISTO ...) > ? -- fim existente  > início novo

Decisões de engenharia aqui:

  • Verificar ≠ otimizar. O sistema responde a uma pergunta de decisão ("este horário é viável?"), que é polinomial, em vez de tentar montar sozinho a agenda ótima da clínica.
  • FIRST 1 faz o banco parar no primeiro conflito encontrado, sem montar a lista inteira.
  • Na recorrência, as r datas são verificadas uma a uma e o usuário escolhe pular os conflitos (pularConflitos). É uma decisão gulosa, local e de custo linear em r.
  • Na edição em lote, todos os conflitos são verificados antes de gravar qualquer coisa ("Nada foi alterado"). É um plano de duas fases que evita estados parciais.

5.3 Onde o PI esbarra em NP

A pergunta natural de uma clínica é: "distribua automaticamente os pacientes da semana entre os profissionais, respeitando especialidade, disponibilidade do terapeuta, preferência de horário do paciente (campo PREFERENCIA), salas e convênio, minimizando janelas vazias."

Esse é um problema de timetabling / alocação de recursos com restrições. Na versão de decisão ("existe uma agenda que satisfaz todas as restrições?") ele é NP-completo, por redução da coloração de grafos: cada sessão é um vértice, sessões que não podem coincidir (mesmo paciente, mesmo terapeuta, mesma sala) são ligadas por arestas, e os horários disponíveis são as "cores". Decidir se o grafo admite k cores é NP-completo para k ≥ 3.

Força bruta: com S sessões e H horários candidatos, há até Hˢ agendas possíveis. Para uma semana modesta (S = 60 sessões, H = 40 horários) isso é 40⁶⁰ ≈ 10⁹⁶ combinações, muito além do número estimado de átomos no universo (~10⁸⁰). Não há hardware que execute isso. Como não se conhece algoritmo polinomial para problemas NP-completos (P vs NP está em aberto), o grupo não busca a solução ótima.

5.4 A heurística adotada (e planejada)

Hoje: a alocação é assistida. A recepção propõe o horário e o sistema decide, em tempo polinomial, se ele é viável. O "problema difícil" fica dividido em muitas perguntas fáceis.

Próximo passo, sugestão automática de horários: uma heurística gulosa de coloração (DSatur / maior grau primeiro):

  1. Ordenar as sessões pendentes pelo número de horários possíveis, da mais restrita para a menos restrita: O(S log S).
  2. Para cada sessão, escolher o primeiro horário livre compatível com terapeuta, paciente e preferência: O(H) por sessão, cada teste usando a verificação de conflito da seção 5.2.
  3. Se não houver horário, a sessão vai para uma lista de pendências que a recepção resolve manualmente.

Custo total: O(S log S + S · H · log A), polinomial, executando em milissegundos para o volume de uma clínica. O preço desse ganho: a solução pode não ser ótima (talvez sobre uma janela que o ótimo eliminaria), mas é boa, rápida e explicável, e o humano continua no controle.

5.5 Outros trade-offs de custo computacional

  • bcrypt para senhas é propositalmente caro (custo exponencial no fator de trabalho). Aqui a lentidão é a defesa: dificulta força bruta. O loginLimiter/loginSlow controlam esse custo no servidor.
  • Google Agenda: quando a API responde 429/403 (limite de requisições), o agenda.js faz novas tentativas com esperas crescentes (backoff), em vez de insistir em laço.
  • LRUCache de pools: memória limitada para N clínicas, com remoção da menos usada em O(1).
  • Paginação obrigatória: nenhuma rota devolve uma tabela inteira, então o custo de cada resposta é limitado independentemente do tamanho do banco.

6. Como a disciplina ajudou no desenvolvimento do PI

Nível 3 → entrada segura
Saber que regex = AFD nos levou a validar todo campo com expressões ancoradas, lineares e com tamanho máximo, e a separar o léxico (formato) do semântico (CPF, data real).
Nível 2 → limites de memória
Entender que JSON exige pilha explicou por que o parser precisa de limite (100 kb) e por que a validação acontece em camadas: sintaxe primeiro, regras depois.
P vs NP → escopo realista
Reconhecer que a agenda ótima é NP-completa evitou que tentássemos um "otimizador perfeito". Escolhemos verificação polinomial agora e uma heurística gulosa depois.

O principal aprendizado de engenharia foi escolher o modelo computacional mais simples que resolve cada problema: AFD onde basta memória finita, autômato de pilha só onde há aninhamento, e heurísticas polinomiais onde o problema exato é intratável. Cada nível acima custa mais memória ou tempo, e a disciplina nos deu as ferramentas para justificar essas escolhas.
