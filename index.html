O projeto

Clínicas multidisciplinares (psicologia, fonoaudiologia, terapia ocupacional, fisioterapia…) costumam controlar pacientes, agendas e repasses com planilhas, agendas de papel e mensagens soltas. O resultado é choque de horários, dados de saúde espalhados sem controle de acesso, retrabalho no faturamento de convênios e falta de indicadores para a gestão.

O VINDIX é uma aplicação web multiempresa, em que cada clínica tem seu próprio banco de dados, e que centraliza tudo isso:

🧾CadastrosPacientes, profissionais e responsáveis, com validação rigorosa de CPF, telefone, e-mail e carteirinha.
📅AgendaAgendamentos únicos e recorrentes, detecção de conflito e sincronização com o Google Agenda.
🩺Consultas e evoluçãoRegistro dos atendimentos e histórico do paciente.
💳Convênios e financeiroGuias, registro ANS, preço por especialidade e repasse dos profissionais.
🔐Permissões granularesCódigos por tabela e por ação, com histórico de cada alteração.
🛡️LGPDCampos sensíveis criptografados, termos de aceite e exportação dos dados do titular.

Validação léxica com AFD NÍVEL 3

Na hierarquia de Chomsky, as linguagens regulares (Tipo 3) são exatamente as que um Autômato Finito Determinístico reconhece, e toda expressão regular pode ser convertida num AFD. Um AFD tem memória constante (só o estado atual) e decide uma entrada de tamanho n em O(n), lendo cada caractere uma única vez. Por isso ele é o modelo ideal para a "porta de entrada" do sistema: todo dado de formulário passa por um reconhecedor regular antes de chegar ao banco.

Teste ao vivo · AFD da data

Esta é a expressão ^\d{4}-\d{2}-\d{2}$ de regras.js como autômato. Digite uma data e veja os estados acenderem um a um.

d = dígito 0–9. Estado inicial q0, estado de aceitação q10 (círculo duplo). Qualquer transição que não está desenhada leva a um estado de erro.

O limite do modelo, e como o código lida com ele

O AFD reconhece o formato AAAA-MM-DD, mas "30 de fevereiro" ou "mês 13" exigem regras semânticas. O dígito verificador do CPF é uma soma ponderada módulo 11.

O grupo separou as duas responsabilidades: a regex faz a análise léxica e uma segunda etapa faz a verificação semântica. Na data, dataValida(a, m, d) monta um Date e confere se ele "volta" igual. No CPF:

export function cpfValido(cpf) {
    if (!/^\d{11}$/.test(cpf) || /^(\d)\1{10}$/.test(cpf)) return false;  // filtro léxico
    for (const t of [9, 10]) {                                           // dígitos verificadores
        let soma = 0;
        for (let i = 0; i < t; i++) soma += Number(cpf[i]) * (t + 1 - i);
        if ((soma * 10) % 11 % 10 !== Number(cpf[t])) return false;
    }
    return true;
}
🔁A retrorreferência/^(\d)\1{10}$/ usa \1, que em geral vai além das linguagens regulares. Aqui o alfabeto é finito e a linguagem tem só 10 palavras (0{11}|…|9{11}). Uma linguagem finita é sempre regular.
➗O CPF também cabe num AFDComo a soma é feita módulo 11, basta guardar (posição, soma mod 11), um número finito de estados. O laço foi escolhido por clareza: os dois têm custo O(n) e memória O(1).
🔑Permissões são regularesOs códigos 1 | 2 | [1-6][0-5] combinam tabela e ação. O middleware exigirPermissao(1, 10, 12) de cada rota funciona como um reconhecedor: a requisição só passa se o usuário tiver um dos códigos.

Segurança: âncoras, limites e ReDoS

  • Todas as regex são ancoradas (^…$), então a palavra inteira precisa pertencer à linguagem. Isso impede conteúdo injetado no meio da entrada.
  • Os campos têm tamanho máximo verificado antes da regex, e as buscas são cortadas em 100 caracteres (filtroBusca).
  • Nenhuma expressão tem quantificadores aninhados ambíguos como (a+)+, que dariam custo exponencial ao motor de backtracking do JavaScript (ataque ReDoS). Todas se comportam como um AFD linear.

Análise sintática e autômatos de pilha NÍVEL 2

Toda a comunicação entre o front-end e a API do VINDIX é feita em JSON. O JSON é uma linguagem livre de contexto (Tipo 2): objetos e listas se aninham em qualquer profundidade, e cada {/[ precisa ser fechado na ordem certa. Pelo Lema do Bombeamento, a linguagem [ⁿ ]ⁿ não é regular: nenhum AFD, com memória finita, consegue "contar" n aberturas pendentes. É preciso uma pilha, ou seja, um Autômato de Pilha.

// server.js
app.use(express.json({ limit: '100kb' }));
// ...
if (status === 413) return res.status(413).json({ erro: 'Conteúdo grande demais' });
if (status < 500)   return res.status(status).json({ erro: 'Requisição inválida' });

O express.json faz o JSON.parse do corpo de toda requisição. Esse parser é descendente recursivo, e a pilha de chamadas faz o papel da pilha do autômato. Um payload mal formado é rejeitado com HTTP 400 antes de chegar a qualquer regra de negócio.

O código do reconhecedor

// Autômato de pilha simplificado: reconhece { } [ ] balanceados, ignorando strings
function balanceado(texto) {
  const pilha = [], par = { '}': '{', ']': '[' };
  let emString = false, escape = false;          // parte finita (um AFD embutido)
  for (const c of texto) {                          // O(n)
    if (emString) { if (escape) escape = false; else if (c === '\\') escape = true; else if (c === '"') emString = false; continue; }
    if (c === '"') emString = true;
    else if (c === '{' || c === '[') pilha.push(c);       // empilha
    else if (c === '}' || c === ']') { if (pilha.pop() !== par[c]) return false; }
  }
  return pilha.length === 0 && !emString;                // aceita com pilha vazia
}
📏Limitando a pilhaNa teoria, a pilha de um autômato é infinita. Num servidor real, não. O limite de 100 kb do corpo limita a entrada e, com ela, a profundidade máxima da pilha. Isso barra payloads gigantes ou aninhados demais (negação de serviço).
🚦Carga sob controletoobusy-js e express-rate-limit recusam requisições quando o laço de eventos do Node está saturado.
🧩Depois da sintaxe, a semânticaUm JSON válido ainda pode estar errado para o negócio. regras.js confere o tipo de cada campo ('deve ser texto', 'deve ser um número inteiro') e aplica as regex da seção 03.
bytes→📚 autômato de pilha→🔤 AFDs por campo→⚖️ regras de negócio→🗄️ banco

Onde o PI esbarra em NP

A pergunta natural de uma clínica é: "distribua automaticamente os pacientes da semana entre os profissionais, respeitando especialidade, disponibilidade, preferência de horário do paciente (campo PREFERENCIA), salas e convênio, e minimizando janelas vazias."

Isso é timetabling, ou alocação de recursos com restrições. Na versão de decisão ("existe uma agenda que satisfaz tudo?") ele é NP-completo, por redução da coloração de grafos: cada sessão é um vértice, sessões que não podem coincidir (mesmo paciente, terapeuta ou sala) são ligadas por arestas, e os horários são as "cores". Decidir se um grafo admite k cores é NP-completo para k ≥ 3.

🧠 Heurística gulosa · S·log S + S·H

Não se conhece algoritmo polinomial para problemas NP-completos (a questão P vs NP está em aberto). Por isso o grupo não busca a solução ótima.

A heurística adotada

Hoje: a alocação é assistida. A recepção propõe o horário e o sistema decide, em tempo polinomial, se ele é viável. O problema difícil vira muitas perguntas fáceis.

Próximo passo, a sugestão automática: coloração gulosa no estilo DSatur, que começa pela sessão mais restrita:

  • Ordenar as sessões pendentes pelo número de horários possíveis, da mais restrita para a menos restrita: O(S log S).
  • Para cada sessão, escolher o primeiro horário compatível com terapeuta, paciente e preferência: O(H) testes, cada um com a verificação de conflito acima.
  • Sem horário possível, a sessão vai para uma lista de pendências que a recepção resolve.
Custo total: O(S log S + S · H · log A), polinomial, em milissegundos para o volume de uma clínica. O preço é que a agenda pode não ser a ótima, mas ela é boa, rápida e explicável, e a decisão final continua com uma pessoa.

Outros trade-offs de custo

🐢bcryptLento de propósito: o custo cresce exponencialmente com o fator de trabalho e dificulta força bruta. loginLimiter e loginSlow controlam esse custo no servidor.
⏳Backoff no GoogleQuando a API responde 429/403, o agenda.js tenta de novo com esperas crescentes, em vez de insistir em laço.
🗃️LRU de conexõesMemória limitada para N clínicas: a menos usada sai em O(1).
📄Paginação obrigatóriaNenhuma rota devolve uma tabela inteira, então o custo de cada resposta é limitado.

Como a disciplina ajudou no PI

🔤Nível 3 → entrada seguraSaber que regex equivale a AFD nos levou a validar cada campo com expressões ancoradas, lineares e com tamanho máximo, e a separar o formato (léxico) do significado (CPF, data real).
📚Nível 2 → limites de memóriaEntender que JSON exige pilha explicou por que o parser precisa de limite (100 kb) e por que a validação é feita em camadas: sintaxe primeiro, regras depois.
⏱️P vs NP → escopo realistaReconhecer que a agenda ótima é NP-completa evitou um "otimizador perfeito" impossível. Escolhemos verificação polinomial agora e uma heurística gulosa depois.

O principal aprendizado foi escolher o modelo computacional mais simples que resolve cada problema: AFD onde basta memória finita, pilha só onde há aninhamento, e heurísticas polinomiais onde o problema exato é intratável. Cada nível acima custa mais tempo ou memória, e a disciplina nos deu as ferramentas para justificar essas escolhas.
